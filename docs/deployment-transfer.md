# Релиз с Telegram transfer helper

Основной модуль остаётся Go + SQLite. MTProto-зависимости находятся только в отдельном модуле `tools/telegram-transfer`; его бинарник называется `telegram-transfer`.

Один основной бинарник обслуживает две независимые systemd-службы:

| Служба | Команда | Работа |
| --- | --- | --- |
| `jardulik-companion.service` | `serve-bot-parser` | Telegram polling, сессия Jardulik, foreground priority, media, проверки анкет, crawl и разрешённые пользователем реакции |
| `jardulik-companion-poster.service` | `serve-poster` | Архивные публикации, private-card repair и отправка уведомлений о доступности |

У служб разные PID; `PartOf`/`Requires` между ними нет. Перезапуск poster не перезапускает бота и парсер. Обе используют тот же environment file, пользователя и SQLite WAL. Poster не делает запросов авторизации или выдачи Jardulik и не получает Telegram updates. Старый `serve` остаётся совместимым all-in-one режимом; role locks не позволяют запускать его одновременно с разделёнными ролями. Разделение описывает новый код и требует отдельной живой приёмки.

CI отдельно выполняет `go test -race ./...` и `go vet ./...` в обоих модулях. Обе программы собираются вне VPS с `CGO_ENABLED=0 GOOS=linux GOARCH=amd64`. Версии checkout/setup-go закреплены существующими SHA; версия Go берётся из корневого `go.mod`, helper использует ту же версию.

`scripts/deploy.sh` требует чистый опубликованный `main`, выполняет проверки обоих модулей и упаковывает только `jardulik`, `telegram-transfer` и явный набор deployment-файлов. Ключи, SQLite, фотографии, API-пара и файл сессии в архив релиза не включаются.

`deploy/install.sh` получает SHA-256 обеих программ. Отсутствующая программа, symlink или неверный хэш останавливают установку. Резерв свободного диска учитывает размер обеих программ. Сначала обе программы копируются и проверяются во временном каталоге релиза; затем каталог атомарно получает имя commit SHA. `SHA256SUMS` содержит две строки.

Расположение после активации:

```text
/opt/jardulik-companion/releases/<commit>/jardulik
/opt/jardulik-companion/releases/<commit>/telegram-transfer
/opt/jardulik-companion/releases/<commit>/SHA256SUMS
/opt/jardulik-companion/current -> releases/<commit>
/opt/jardulik-companion/previous -> releases/<previous-commit>
```

Обе программы переключаются одним `current` symlink. Перед заменой unit-файлов обычная установка сохраняет их исходные версии, enablement и состояния служб, затем останавливает обе runtime-роли. Старый all-in-one процесс должен завершиться до переключения. После установки запускаются и проверяются обе новые роли. Таймер по-прежнему вызывает `backup-daily`, который только ставит задание в БД; передачу выполняет poster.

При неудачном запуске или переключении установщик останавливает новые роли, возвращает прежний `current` и точные старые unit-файлы. Запускаются только роли, которые были активны до попытки. При первом переходе это старый all-in-one unit, а новый poster unit удаляется. Если восстановить файлы или подтвердить остановку не удалось, прежние роли автоматически не запускаются. Исходные unit-файлы и состояния остаются в закрытом каталоге `/opt/jardulik-companion/deployments/<commit>.<suffix>/`; этот путь выводится установщиком. Это также позволяет согласованно откатить более поздний релиз вручную, вернув и бинарники, и соответствующие units. Один откат symlink к старому `serve` без возврата units недостаточен.

`scripts/deploy.sh --no-start sg-1gb` требует, чтобы обе runtime-службы уже были `inactive` с `MainPID=0`; отсутствующий poster допускается при первой миграции. Этот режим ставит units и переключает релиз без `start`, `restart`, `enable`, health CLI или запуска таймера. Ошибка возвращает старые units и symlink, сохраняя остановку. Environment file, SQLite и состояния публикаций установщик не меняет.

Первый переход выполняют после остановки старого процесса между запросами и публикациями. Неопределённые отправки не очищают и не ставят повторно скриптом деплоя: для них остаётся отдельная проверка доставки. Автоматическая ротация старых релизов, snapshot units и Telegram-документов не добавляется.

Настройки остаются вне Git в защищённом environment file:

- `TELEGRAM_TRANSFER_HELPER` по умолчанию `/opt/jardulik-companion/current/telegram-transfer`.
- `TELEGRAM_TRANSFER_SESSION_FILE` по умолчанию `APP_DATA_DIR/telegram-bot-session.enc`.
- `TELEGRAM_API_ID` и `TELEGRAM_API_HASH` задаются парой; значения и bot token не передаются аргументами командной строки.
- Сессионный файл helper шифруется отдельным контекстом существующего `SESSION_KEY`.

Helper запускается только для отдельной передачи, не создаёт daemon или локальный Bot API сервер. Наличие и SHA бинарника не доказывают успешный MTProto-вход или отправку: для этого нужна отдельная согласованная живая проверка с настроенной API-парой.

У каждой роли `MemoryMax=128M`, `MemoryHigh=96M`, `GOMEMLIMIT=64MiB`, `GOMAXPROCS=1`. Дочерний helper разделяет лимит poster. При приёмке измеряют одновременную сумму памяти обеих служб во время загрузок/ZIP/передачи, пики каждой cgroup, OOM events и свободную память всего VPS. Пики разных моментов не являются измеренным общим пиком. До этих замеров нет подтверждения общего бюджета для VPS 1 ГиБ. Сборка на VPS, новые порты и отдельный сервер БД не добавляются.

Локальная проверка скриптов без сервера:

```sh
bash -n deploy/install.sh scripts/deploy.sh
python3 scripts/test-deploy.py
```

Mock-проверки покрывают отказ для dirty main и непроверенного staging path, отдельные проверки nested module, остановку при ошибке helper build, отсутствие секретных файлов в пакете, проверку двух SHA, остановку старого процесса до замены units, отказ при любой активной роли в `--no-start` и возврат пары бинарников вместе с legacy/split units при неудачном запуске. Запуск этих проверок не выполняет SSH, systemd или Telegram API в реальной среде.
