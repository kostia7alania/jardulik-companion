# Индексы архивных анкет

Один тред `📚 Каталог`, два вида: `🧩 Совместимость` и `🎂 Возраст`. Строки находятся в свёрнутой цитате. Формат: `37 ♑️ 19, Сабина, 70% ⭐️`. Номер, знак, возраст, ФИО и процент образуют одну ссылку на подтверждённый архивный пост в конкретном треде; последний значок статуса находится вне ссылки. Из исходного числового `type`: `1` → `⭐️`, `0` → `⚪️`, отсутствующее или неподдерживаемое значение → `❔`. Фамилия берётся из `surName` или `surname`, родственные фамилии не добавляются.

Процент берётся из сохранённого ответа GPT для текущего аккаунта владельца и этой анкеты. Проверяются ID обоих участников, используется тот же разбор оценки, что в посте совместимости. Для доступной анкеты берётся последний успешный ответ; неоднозначный ответ даёт `—`. Для недоступной анкеты допустим последний распознанный успешный процент без нового GPT-запроса. Такое исключение требует отрицательного результата проверки в последнем цикле с текущими owner/upstream/generation; одного старого `profile_presence` недостаточно. Известный `0%` сохраняется.

Первый индекс сортируется по убыванию оценки, неизвестные значения идут в конце. Второй по возрастанию возраста, а внутри одного возраста по дате рождения от более поздней к ранней. Затем применяются стабильные имя и ID. Значок зодиака определяется по обычным календарным границам из проверенной даты рождения, включая дни на границе знаков. Неизвестная, некорректная или будущая дата даёт фиксированный `❔`. Ограничение ±2 дня в персонализированных приветствиях не изменяется.

Индекс содержит текущие поля сохранённых анкет того же владельца, имеющих подтверждённый архивный пост. Ссылка выбирается из последней подтверждённой публикации по исходному времени публикации; повторная загрузка ZIP её не переставляет. Для собственной дублирующей версии допустим подтверждённый оригинал с теми же profile ID, непустым fingerprint и thread ID; поля анкеты и оценка остаются от текущего владельца. Новая ожидающая или дублирующая версия не скрывает предыдущий архив. Недоступные анкеты остаются в списках.

Один worker в роли poster обновляет снимок раз в пять минут, выполняет по одной Telegram-операции за проход и использует общий архивный mutex и pacing. RichMessage вмещает до 32768 символов UTF-8; используются два блока: заголовок и свёрнутая цитата. Без RichCards действует классический предел 4096 UTF-16. Страницы появляются только при исчерпании текстового бюджета, ограничения по 50 строк нет. Сортировка и номер строки глобальны для всего вида. Новые исходные анкеты и расчёты подхватываются следующим обновлением; запросы Jardulik или GPT здесь не выполняются.

`profile_index_topics` хранит forum thread ID с owner/upstream/generation/chat binding. Новый аккаунт создаёт только compatibility topic, называемый `📚 Каталог`. Нечётные физические страницы содержат совместимость, чётные возраст. `profile_index_pages` хранит page number, message ID, точный желаемый payload и подтверждённый hash. Неизменившаяся страница не отправляется повторно, изменившаяся редактируется по её прежнему ID. При переходе с двух тредов старый compatibility topic становится Каталогом; его первые два сообщения используются для двух видов. Остальные известные сообщения, включая старый age topic, сохраняют строки и ссылки в свёрнутом архивном виде со ссылкой на Каталог. Архивные сообщения не удаляются и могут быть повторно использованы, если список вырастет. Старый замороженный манифест публикации не переписывается.

Подтверждение имени известного треда хранится в `meta` с ключом `profile_catalogue_title:<owner>:<upstream>:<chat>:<thread>`. Переименование идемпотентно; отдельной новой таблицы нет. Публикационный манифест ждёт подтверждённые страницы и имя Каталога. Непубликованные устаревшие страницы с точной причиной `unpublished_page_superseded` в него не попадают; неизвестные исходы отправки сохраняются и блокируют завершение.

Неизвестный исход создания треда или нового сообщения, включая 5xx, сохраняется как `uncertain` и требует сверки, без слепого повтора. Правка известного message ID идемпотентна: транспортные сбои и 5xx можно повторить. ACK проверяется по ожидаемым chat/thread/message IDs. Перед каждым внешним действием повторно проверяется текущая привязка аккаунта.

Весь журнал входит в SQLite-бэкап. Для daily fingerprint достаточно новых topic/page ID; повторы, `sent_sha`, payload правок и retry timestamps не должны сами создавать новые бэкапы. Операторская остановка перед релизом должна дождаться отсутствия `preparing/sending` в обеих таблицах.

Неподтверждённые новые операции `sending/uncertain` с нулевым thread/message ID входят в отдельные семантические записи fingerprint. Поэтому `--if-changed` сохраняет журнал запрета повтора даже без новых анкет; повторы правки уже известного message ID и их технические timestamps по-прежнему не создают лишний бэкап.
