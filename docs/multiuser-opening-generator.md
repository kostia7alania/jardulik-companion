# Персональные открывалки для нескольких пользователей

Статус: проект, 10.11.2026. Генератор, платные вызовы и коммерческий доступ этим документом не включаются. Реализация должна готовить небольшой запас проверенных текстов отдельно от отправки реакций. Для каждого подключённого пользователя сохраняются его настройки, собственный контекст и независимый бюджет.

Целевой результат: после подключения и явного включения пользователь видит примеры в своём стиле; новые подходящие анкеты постепенно получают текст с настоящей зацепкой из анкеты и отдельной проверкой. При лайке выбирается уже сохранённый текст. Завершение генерации само по себе никому не отправляет сообщение и не запускает авто.

## Что уже есть

Основа: [персональные приветствия](personalized-greetings.md), [draft cache](../internal/companion/reaction_messages_drafts.go), [выбор и outgoing intent](../internal/companion/reaction_messages.go), [существующий worker](../internal/companion/compatibility_worker.go).

Проверено по текущему исходному коду, без обращения к рабочей БД или внешним сервисам.

| Готово в v1 | Источник и граница |
|---|---|
| Изоляция пользователей, текущий Jardulik account, private-chat `/start` | `Service.handle`, `sessions.owner_id`; `Config.OwnerID` остаётся оператором, а не единственным пользователем |
| Настройки `telegram_username`, `prefer_drafts`, `iron_mix` отдельно по владельцу | `ReactionMessagePolicy`, `ConfigureReactionMessagePolicy` |
| Архив проверенных текстов и точных материалов двух проходов | `reaction_message_drafts`, `ImportReactionMessageDrafts`; сейчас это импорт готового пакета, не LLM worker |
| Строгие восемь исходных полей | `reactionDraftBasis` / `reactionDraftContent`: `name`, `age`, `height`, `description`, `profession`, `city`, `country`, `languages` |
| Кэш для owner/account/target/handle/strict8 и fallback | `reactionDraftMessageTx`, `preparePositiveMessage`; при `prefer_drafts=true` выбирается approved, иначе `birthday` |
| Adult guard, неавтоматическое снятие hold, точный outgoing intent до POST | `reactionDraftHoldTx`, `birthdayGreetingMinorDOB`, `reaction_messages_hold.go`, `reaction_messages_positive.go` |
| Локальное Iron-приветствие | `ironMixReactionMessage`; сейчас меняется известное начало, не переводится всё сообщение |
| SQLite WAL, короткие DB claims, recovery и фоновые роли | `schema.sql`, `OpenStore`, `ClaimCompatibilityJob`, `RecoverCompatibilityJobs`, `RunBackground` |

LLM provider client, очередь такой генерации, её per-user onboarding и платёжные entitlement в просмотренном коде не найдены. Существующие два прохода и подготовленные тексты доказывают формат заготовки, но не качество будущего автоматического генератора для всех пользователей. Число готовых текстов не запрашивалось из БД в рамках этого дизайна.

`/GPT/checkCompatibility` принимает пару Jardulik-пользователей для расчёта совместимости. Он не считается API произвольных prompts. Генератор не вызывает его, не получает через него доступ к другой модели и не расходует Огни Jardulik.

## Минимальная схема работы

Один новый Go worker в существующем приложении, одна SQLite и стандартный `net/http`. Без агентного фреймворка, отдельного брокера, векторной БД и новых зависимостей. Provider adapter имеет только ограниченную операцию batch generation; он не получает инструменты, доступ к Telegram, Jardulik credentials или возможность отправить реакцию.

```text
/start → подключение → настройки и примеры → отдельное включение генерации
                                      ↓
сохранённые анкеты → planner → draft batch → check batch → local gates → approved cache
                                                                          ↓
                           отдельно включённый like/autolike → точный intent → POST
```

По функциям: восприятие и память light, рассуждение light в двух ограниченных проходах, действие none у генератора, проверка и границы heavy. Дополнительный проход нужен для проверки готового текста и источников. Он не означает запуск команды агентов или гарантию независимости двух ответов одной модели.

## Подключение и настройки

1. `/start` создаёт обычного пользователя. Подключение Jardulik проходит существующую проверку Telegram identity. Коммерческий доступ проверяется отдельно от успешного подключения.
2. Пользователь явно подтверждает свой Telegram username. Начальное значение можно предложить из его Telegram update, но без username поле остаётся пустым. Нельзя подставлять handle оператора. Проверка формата не доказывает владение username; UI просит подтвердить адрес перед использованием.
3. Язык: русский или русский с Iron-приветствием. Iron не выбирается по имени, городу, языку анкеты или происхождению. В первой версии используется только уже подтверждённое `дӕ бон хорз`, остальной текст русский.
4. Стиль задаётся тремя короткими настройками: обращение на ты/вы, спокойнее/легче, emoji выключены/редко. Пользователь может добавить до двух своих примеров, суммарно до 1000 UTF-16. Чужая переписка для этого не загружается.
5. Бот показывает выбранные поля собственной анкеты и даёт исключить их из контекста. Это источник интересов и допустимых фактов о себе, а не автоматическая диагностика стиля. В первой версии allowlist: `name`, `description`, `profession`, `city`, `country`, `languages`. Каждое утверждение от первого лица должно иметь подтверждение в выбранных полях или явно введённых владельцем фактах.
6. До платных запросов показываются выбранный оператором провайдер, какие поля отправляются, доступный лимит и отдельное подтверждение подготовки текстов. Согласие связано с версией этой конфигурации. Сейчас провайдер и бюджет не выбраны, поэтому эта часть не активирована.
7. После включения готовятся три примера для просмотра. Кнопки: `Подходит`, `Попроще`, `Изменить стиль`, `Приостановить`. Оценка касается настройки, не отправки. Персональные тексты и запуск авто включаются раздельно.

Экран состояния: сколько текстов готовы, сколько ждут, сколько используют шаблон, остаток дневной квоты, ближайшая причина ожидания. Например: `Готово 12 · В очереди 8 · Шаблон 4`. Не писать `сгенерировано`, если имеется только очередь или шаблон.

Если provider key отсутствует, `blocked_provider` объясняется как недоступность генерации. Остаётся существующая библиотека `birthday`, если пользователь отдельно включил сообщения; очередь содержит только ограниченные локальные задания. Сохранённые актуальные approved-тексты остаются доступны. Настройка и накопление очереди не запускают лайки.

## Входные данные и два прохода

Target snapshot использует ровно существующие восемь полей и существующий Go hash. Не добавлять фотографии, GPS, расстояние, mutable photo URLs, контакты, всю анкету, расчёт совместимости или содержимое других диалогов. `birthday` не входит в prompt: локально он используется только действующим adult guard. Проверка возраста и актуальных фильтров выполняется до постановки и перед публикацией результата в кэш.

Own context содержит только подтверждённую allowlist-проекцию и настройки. Ни `Session`, ни `account_json` целиком, ни исходные credentials в prompt не сериализуются. Все анкетные строки и пользовательские примеры являются данными: вложенные команды не меняют формат запроса, доступные поля или правила проверки.

Для каждого поля сохраняются оригинал, locator `owner/upstream/profile/version/field` и точное значение. В сеть уходит ограниченная проекция. Если текст не помещается в бюджет входа, передаётся явно отмеченный точный фрагмент с offsets; весь strict8 snapshot остаётся локально, его hash не пересчитывается по усечённой версии. Непереданную часть нельзя использовать как evidence в ответе.

Одна batch содержит до четырёх анкет одного владельца. Смешивать владельцев в одном prompt нельзя. Во все ответы входит opaque `item_id`, заданный сервером. Отсутствующий, повторный или чужой item не присваивается соседней анкете.

Проход draft возвращает для каждой анкеты:

- `body`: короткая открывалка с одним лёгким конкретным вопросом, без greeting и Telegram CTA;
- `basis_quality`: `personal` или `limited`;
- `target_evidence` и, при фактах о себе, `own_evidence`: field и точная quote;
- `angle`: короткий редакционный тег, например music или travel; это не психотип.

`personal` требует настоящей содержательной зацепки. Для пустого описания допустим `limited`: обычный вопрос без выдуманного хобби и без заявления, что текст глубоко персонализирован. Возраст, рост и имя сами по себе не становятся комплиментом характеру. Нельзя придумывать факты от имени отправителя, совместимость, психотипы, чувствительные свойства, Human Design, натальную карту или черты по дате рождения.

Проход check получает тот же разрешённый snapshot, первый ответ и контракт. Он возвращает решение по каждому item, финальный `body`, evidence и короткие причины. Он проверяет смысл зацепки, естественность, отсутствие нажима, повторов внутри batch и неподтверждённых утверждений. Нужна отдельная версия prompt; модель может быть той же, поэтому автоматический check не называется независимой человеческой редактурой.

Local gates после check:

- строгий JSON и соответствие item/context; `personal` имеет evidence;
- каждая quote буквально присутствует в переданном поле именно этого snapshot;
- один `?`, корректный UTF-8, отсутствие других username/URL, шаблонных placeholders и запрещённых полей;
- сервер добавляет корректное имя, согласованное приветствие и ровно один CTA с текущим `@owner_handle`;
- весь конечный текст после подстановки имени, CTA и Iron-render снова проходит проверку одного вопроса и только своего handle, не превышает 500 UTF-16; небезопасное значение имени пропускается, а не обходится валидатор;
- повторяющееся нормализованное body или почти одинаковые body среди последних 20 текстов этого владельца отклоняются; порог near-duplicate является версионированной редакционной эвристикой и проверяется на пилоте;
- повторная проверка owner/account/generation, hashes, pause, entitlement, актуальных adult filters и active hold.

Проверка подстроки подтверждает цитату, но сама по себе не подтверждает её интерпретацию. Поэтому смысл проверяет второй проход, а выпуск генератора требует ручной выборки. Если второй проход не смог доказать зацепку, item становится `needs_review` или `limited`, а не approved с придуманным обоснованием. Школьный класс или курс сами по себе не создают возрастной hold. Существующий hold снимается только существующей отдельной процедурой; LLM не снимает его и не переписывает исходный профиль.

Автоматический цикл ограничен draft → check. Не прошедший item не крутится в бесконечной саморедактуре: fallback либо просмотр пользователем. Новая попытка по тем же данным создаёт следующий append-only attempt того же job после явного разрешённого перехода; прошлый attempt сохраняется. Меняются данные или стиль, значит появляется новый context и новый job. Unknown нельзя обойти таким переходом без сверки прежнего запроса и его бюджетной резервации.

## Cache identity и необходимая миграция

Существующий `content_hash` strict8 сохраняется без изменений. Полный binding нового результата:

```text
body_context_hash = SHA256(canonical JSON {
  schema: opening-body-v2,
  owner_id, upstream_id, target_profile_id, target_content_hash,
  selected_own_context_hash, explicit_body_style_hash,
  draft_provider, requested_draft_model, draft_prompt_version,
  check_provider, requested_check_model, check_prompt_version,
  output_schema_version, semantic_validator_version
})
context_hash = SHA256(canonical JSON {
  schema: opening-render-v2, body_context_hash,
  telegram_username, language_mode, renderer_version, render_validator_version
})
```

Хеши вычисляет Go, не модель. `requested_model` описывает конфигурацию задания; фактически возвращённое имя каждой модели сохраняется отдельно. Если провайдер возвращает неопределённый alias без доступной immutable revision, это ограничение остаётся в аудите; нельзя объявить alias неизменяемой версией модели. Если actual model не сообщена и не подтверждается контрактом выбранного endpoint, audit хранит unknown, а выпуск не проходит gate идентифицируемой модели. В полный exact request hash входит реально отправленное тело.

У v1 `UNIQUE(owner_id,upstream_id,profile_id,telegram_username,content_hash,state)` не позволяет сохранить новый текст при изменении только собственного стиля или prompt. Произвольная запись context в `provenance` не исправляет текущий lookup.

Нужна одна versioned migration `reaction_message_drafts` на v2 с колонками `context_hash NOT NULL`, `body_context_hash`, `origin` (`import_v1`/`generated_v2`), `base_body`, `quality`, `job_id`, а также unique по `owner/upstream/profile/content_hash/context_hash/state`. Базовый `basis_hash` v1 остаётся исторической проверкой, v2 lookup дополнительно требует точный `context_hash` и текущий handle. Миграция сохраняет прежние draft ID, `capture_json`, SHA и ссылки `reaction_message_hold_resolutions`; проверяется на копии БД с `foreign_key_check`. Слепое добавление колонки при сохранении старого unique не годится.

Legacy approved не получают выдуманную модель или generated context. Они сохраняют происхождение `import_v1` и ненулевой `context_hash = "legacy:" + reactionDraftBindingHash(...)`. Такой же binding вычисляет v1 import после миграции, поэтому повтор старого пакета сохраняет idempotency, а SQL NULL не обходят UNIQUE. `body_context_hash` у legacy пустой; эти строки не используются для бесплатного body reuse. После включения персонального SaaS-стиля их можно использовать только как явно выбранный legacy fallback, а не выдавать за результат новых настроек. Existing holds остаются account/profile scoped независимо от нового context и версии текста.

Что инвалидирует результат:

| Изменение | Действие |
|---|---|
| Любое из восьми target fields | Старый текст остаётся в истории, enqueue нового context |
| Выбранное поле own context или явный стиль | Новый context и новое ограниченное задание |
| Только handle или ru/Iron greeting | Новый final context и локальный render из generated_v2 approved `base_body` с точно тем же `body_context_hash`; paid generation не нужна, все local gates повторяются |
| Только баланс, URL фото, distance, время просмотра | Никакой регенерации |
| Prompt/model/validator version | Новые задания используют новую версию; старый context не выбирается как новый; массовый backfill не запускается автоматически |
| Pause, disconnect, смена Jardulik account | Новая выдача запрещена до свежего binding; старый result не переезжает к другому upstream |
| Изменение фильтров | Не меняет текст, но меняет eligibility и очередь; перед отправкой фильтры проверяются заново |

Session generation не входит в semantic cache key, но входит в claim/preflight и completion guard. Повторное подключение того же account может повторно использовать cache только после проверки актуального account/profile/style binding. Completion старой generation не публикуется автоматически.

## Хранение, очередь и аудит

Кроме cache v2 нужны три маленькие таблицы, все с `owner_id` FK `ON DELETE CASCADE`:

| Таблица | Что хранит |
|---|---|
| `opening_settings` | enabled, собственные выбранные поля/факты/примеры, style revision, provider-consent revision, owner cap, scheduling cursor, last_served_at. Коммерческие plan/entitlement поля меняет только доверенная admin/billing часть, не callback пользователя |
| `opening_jobs` | owner/upstream/target/version/generation, strict8/context/request hashes, точные разрешённые snapshots, state/phase, lease/nonce, priority, next_at, ссылки на бюджетные attempt/reservation, итоговый draft ID. `UNIQUE(owner_id,context_hash)`; failed job получает новый attempt, не duplicate job |
| `opening_attempts` | append-only draft/check attempt: exact body и полный raw response, request ID, provider, requested и actual model, HTTP status, usage, timestamps, error class, billed/estimated/reserved cost, price-version |

Имена таблиц и полей выше являются спецификацией, они ещё не реализованы. Привязка job → attempt проверяется по owner и nonce, не только по числовому ID. Batch request хранится один раз в attempt с точным списком item bindings; все jobs этой batch ссылаются на этот attempt, но стоимость учитывается один раз. Его нельзя отдать другому владельцу через status/export. Секретный Authorization header в audit не копируется. Успешный approved результат обязан ссылаться на полный сохранённый ответ обоих проходов; raw source не заменяется summary.

Логические состояния: `queued_draft → draft_inflight → queued_check → check_inflight → approved`. Отдельно `blocked_provider`, `blocked_budget`, `paused`, `stale`, `needs_review`, `failed`, `unknown`. HTTP attempt получает собственное `prepared/sending/received/unknown`; item не становится approved только по HTTP 200 или наличию поля body.

Planner читает уже сохранённую очередь/избранное. Он не запускает новый Jardulik crawl и не запрашивает `/getMe` или `/getUser` ради LLM. Первым готовит текущий preview, затем избранное и ближайшие ещё не обработанные анкеты по текущим фильтрам. После использования текста пополняет запас. Цель первой версии: до 20 актуальных текстов на пользователя, а не генерация на весь архив.

## Fair scheduling и маленький VPS

Предлагаемые стартовые пределы для пилота, не измеренная ёмкость и не обещанный тариф:

- один provider HTTP request глобально, одна in-flight batch на владельца, до четырёх items в batch;
- не более 20 items оплаченной генерации на владельца за скользящие 24 часа; новая generation для изменившегося context тоже занимает item; пользователь может уменьшить предел. Стадии и повторные попытки учитываются также в денежном бюджете;
- до 100 queued items на владельца и 1000 в общем backlog; дальнейшие анкеты остаются в source queue без фиктивных generated rows;
- planner читает до 32 кандидатов за тик, worker выбирает eligible owner с самым старым `last_served_at`; после каждого HTTP stage ставит владельца в конец очереди. Check готового draft имеет приоритет внутри его следующего turn, но не монополизирует все turns;
- hard HTTP timeout 45 с, lease 2 минуты, request до 64 KiB и response до 256 KiB. Конкретные token ceilings задаются выбранным provider adapter;
- пауза при недостатке свободного диска и высокая приоритетность пользовательских операций. Никакого scan полного raw-response архива на каждом тике.

Используется existing WAL и один короткий writer. Claim, reservation и `RowsAffected==1` фиксируются транзакцией; provider HTTP выполняется после commit, без DB tx и без долгого `userLock`. Перед записью результата короткая транзакция повторяет binding checks. Pause останавливает новые attempts; уже отправленный запрос может потребить бюджет, его ответ сохраняется в audit без публикации до resume и свежей проверки. Удалённый во время запроса owner не создаётся заново completion-кодом, результат не восстанавливает удалённые данные. Нельзя целиком копировать `compatibilityStep`, который держит owner mutex во время source HTTP: медленная модель иначе блокировала бы foreground пользователя.

Для single-host v1 достаточно одной роли worker с существующим role lock. Startup recovery не сбрасывает живые запросы другого процесса. Восстановление expired prepared claim без отметки sending безопасно; sending после падения становится unknown. Второй экземпляр процесса не начинает платные запросы до получения эксклюзивной роли.

Нужно измерять RSS, рост WAL/БД, latency меню, очередь по owner и p95 ожидания готового текста. Ограничение concurrency и batch подходит как старт для 1 GB VPS, но доступная пропускная способность проверяется нагрузочным пилотом. Масштабирование сначала увеличивает лимиты после измерений, а не добавляет инфраструктуру заранее.

## Деньги и повторные запросы

Server config должен явно задавать provider, обе model ID, endpoint из operator allowlist, секрет вне пользовательской БД, prompt versions, hard token ceilings, версию тарифов, общий дневной денежный предел и per-owner allowance. Эти параметры отсутствуют в текущей реализации. Пользователь не передаёт произвольный endpoint или ключ через чат. Конкретный провайдер и цена сейчас не рекомендуются и не предполагаются.

Перед первым paid POST batch одна транзакция создаёт пару reserve-записей draft/check в `opening_attempts`, по известным input/output token ceilings и выбранному тарифу. Check использует уже существующий резерв этой пары; повторное прохождение scheduler не резервирует его заново. Вход учитывает prompt overhead и все items; check bound включает максимально допустимые draft body и evidence, ещё не известные при первом резерве. Adapter обязан уметь обосновать token bound по контракту выбранного API; приблизительный счётчик символов не является гарантией денежного потолка. Если тариф или потолок неизвестны, состояние `blocked_budget`, без HTTP.

В каждой budget-check транзакции выполняется `spent + unsettled_reservations + new_reservation <= cap` отдельно для owner и глобально. Ledger `opening_attempts` является единственным денежным источником; job хранит ссылки, а не второй независимый баланс. Фактический usage атомарно заменяет reservation на settled cost один раз. При известном отказе до sending неиспользованный резерв освобождается один раз. Если check не потребуется, освобождается только его неиспользованный резерв. При неизвестном usage сохраняется консервативная резервация и признак pending reconciliation; смена суток её не обнуляет. Метрики разделяют target items, attempts, actual tokens и деньги; batch из четырёх не объявляется одним бесплатным текстом. Reject/check/retry тоже стоят денег и входят в cap.

DB idempotency не доказывает provider idempotency. Exact request и unique attempt фиксируются перед сетью. При timeout после sending нельзя понять, был ли запрос обработан и оплачен: attempt становится unknown, резерв сохраняется, автоматический новый paid POST не делается. Provider request-id lookup или idempotency key используется только если выбранный API действительно это поддерживает. Явно полученный rate-limit может иметь ограниченный backoff; допустимость и учёт повторного POST определяет adapter, а не общая вера в безопасность retries. Один job имеет последовательные attempt numbers и unique `(owner_id, batch_key, phase, attempt_no)`; append-only audit не стирает предыдущую попытку. Дедупликация одного attempt отличается от разрешения нового оплачиваемого attempt.

Если draft записан, а check не начат, после рестарта выполняется только check. Если ответ пришёл, но commit результата не подтверждён, сначала сверяется сохранённый attempt, затем статус provider, если такая операция существует. Из unknown не создаётся approved, не расходуется реакция Jardulik и не запускается autolike. Ранее отдельно включённый auto может продолжить только со свежим approved или существующим разрешённым template fallback, а не с текстом неизвестного результата.

Предельный размер ответа защищает процесс и диск. Для обычного результата сохраняется полный raw response до approval. Overflow или обрыв помечается как incomplete, сохраняется точная полученная часть с этим признаком; такой ответ не может стать approved и не называется полным аудитом. Тела и source quotes не пишутся в общие логи. Новые таблицы включаются в backup, owner export и удаление до live rollout.

## Выпуск и проверяемые критерии

1. Сначала migration и offline fixture adapter. Тесты двух владельцев с одинаковым target ID и разными handles/styles: ни cache hit, ни item из batch, ни status/export не пересекают tenant.
2. Контрактные тесты strict8, own/style/model/prompt invalidation; смена photo URL или баланса не вызывает paid job. Handle/Iron-only render не вызывает provider. Старый manual approved и hold сохраняются после migration с теми же ID и SHA.
3. Crash tests после claim, sending, draft commit и check response; concurrent enqueue и duplicate batch response не дублируют attempts/cache. Unknown не повторяется и не снимает reservation.
4. Deterministic gates: UTF-16 с emoji, один вопрос и свой handle, точная source quote, unknown fields, prompt injection в description, неполная batch, changed profile/generation, pause, expired entitlement, invalid/minor DOB и active hold.
5. Ограниченный live pilot включается только после выбора провайдера и бюджета. Человеческая проверка первых 30 готовых текстов: 10 содержательных, 10 коротких, 10 пустых анкет; разные стили и оба режима greeting. Ноль чужих handles, выдуманных фактов, возрастных нарушений и критических attribution ошибок. Не менее 27 из 30 владелец принимает без содержательной правки; это предлагаемый release gate, не достигнутая метрика.
6. Fairness test с активными владельцами и заполненной очередью: никто не получает второй HTTP turn, пока eligible peers не получили первый; foreground меню не ждёт model HTTP. На целевом VPS фиксируются реальный RSS, очередь, меню и стоимость готового approved текста.

Небольшой план реализации: сначала cache v2 + settings/queue migration, затем deterministic pipeline с fake adapter, затем provider adapter и audit/budget ledger, затем Telegram preview/status и pilot. Это несколько последовательных изменений существующего Go приложения. Денежную себестоимость и срок по дням до выбора API и объёма нового UX достоверно назвать нельзя.

Аварийное выключение останавливает новые paid attempts и enqueue, сохраняет raw audit и актуальные approved. При необходимости перестаёт использовать generated_v2 cache; действующие manual drafts и birthday fallback остаются отдельными существующими возможностями. Отправка реакций выключается своим существующим переключателем.

## Решения перед live-включением

Нужно выбрать LLM provider и точные модели draft/check, установить его server API key в конфигурации сервера и утвердить глобальный денежный бюджет с per-user лимитами. Ключ не запрашивается у пользователей через чат. До этого платные LLM-запросы запрещены конфигурацией.

Также нужны согласованная внешняя проекция данных и consent, коммерческий entitlement/trial, политика fallback и проверенные версии prompt/validator. Настройка сервера и отдельный opt-in пользователя обязательны; одного наличия ключа недостаточно.

Текущий template fallback работает в существующем режиме сообщений. Автоматическая LLM-генерация для всех подключённых пользователей пока остаётся дизайном из этого документа, не реализованной возможностью.
