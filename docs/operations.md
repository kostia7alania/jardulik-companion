# Сервер и ошибки в Telegram

Операторский тред `🖥 Сервер · логи` привязан к `OWNER_TELEGRAM_ID` и существующей архивной группе. Клиенты сервиса к нему доступа не получают.

Первое сообщение закрепляется и редактируется примерно раз в минуту. В нём видны heartbeat трёх основных ролей, состояние подключения, этап суточного цикла, проверка анкет, расчёты, архивная публикация, оформление карточек, Каталог, открывашки и бэкапы. При запуске отдельного HTTP-режима появляется четвёртая строка Mini App с независимым heartbeat. Ошибки оформления показывают ID задания и причину, чтобы зависший этап не выглядел продолжающимся поиском. Время выводится в UTC+3 с днём недели.

WARN/ERROR сохраняются локально, затем попадают в устойчивую SQLite-очередь. Она также учитывает ошибки, которые другие воркеры записывают только в свои outbox. Повтор одной ошибки обновляет её прежний пост: число повторов, первое и последнее наблюдение. Технические поля находятся в свёрнутой цитате. Сообщения и история автоматически не удаляются.

Ошибки загрузки фото группируются по аккаунту и причине. В свёрнутой цитате указан ID последнего задания. Если источник вернул HTML, это видно в заголовке. В закрепе видны число загруженных файлов, ошибки и оставшаяся очередь.

Монитор читает локальные данные и использует общий Telegram pacing. Он продолжает работать при паузе публикации, отключённой сессии и blocked-цикле; запросов Jardulik, GPT или реакций не делает. Новый тред или сообщение с неизвестным исходом не отправляются повторно вслепую. Правки подтверждённых message ID можно повторять после транспортного сбоя. Все внешние действия проверяют owner/chat/thread binding; SQLite-транзакция во время HTTP не удерживается.


## Восстановление после сбоя

Система перезапускает упавшую роль через 10 секунд. При повторных падениях интервал растёт до двух минут. Внутри роли завершившийся воркер запускается снова через 10 секунд. Временная ошибка записи SQLite откладывает обход на последней сохранённой странице. Если запись самой остановки не удалась, воркер повторяет эту запись перед следующим запросом.

После сохранения квитанции ZIP постер может продолжить отправку карточки с того же места. При явном отказе Telegram обработать изображение он отправляет обычный альбом, при повторном отказе публикует текст. Исходные фотографии остаются в ZIP. Если подтверждение доставки потерялось, карточка остаётся в очереди на сверку. Закреп показывает дату цикла, который публикуется сейчас, причину блокировки карточки и последний полный цикл. Для бэкапов показывается отдельно результат последней попытки.

Если источник фотографий вернул 429 или 5xx, загрузка повторяется с паузой. При числовом Retry-After пауза учитывает значение сервера.
