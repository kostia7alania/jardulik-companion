# Telegram-ссылки после взаимности

Проверено 9.11.2026 через аккаунт владельца в официальном @jardulik_bot и по публичной сборке index-BFeBP-cW.js.

1. Экран взаимностей получает список через GET /user/getReactUsers с isMutual=true.
2. Кнопка Telegram вызывает POST /telegram/getTG с внутренними fromUserId и targetUserId Jardulik. Это действие запрашивает отправку карточки, а не обычное чтение JSON анкеты.
3. Frontend не использует ответ как контактный URL: после запроса он закрывает Mini App. Контактная карточка видна в личном диалоге с официальным ботом.
4. Посмотреть анкету является web_app-кнопкой с URL вида https://mini.jardulik.app/mutuals?targetUserId=<id>&noCheck=1. Telegram добавляет свежие подписанные launch-параметры. noCheck=1 не доказывает взаимность; для маршрута mutuals frontend его не использует.
5. Открыть в Telegram содержит отдельную обычную ссылку https://t.me/<username>. Проверенный переход открывает личный диалог.

Связь ID Jardulik с Telegram numeric ID не выводится из номера анкеты или username. Шаблон start/startapp для произвольной анкеты в просмотренной сборке не подтверждён. Кнопка запуска от другого бота не эквивалентна запуску от официального Jardulik: подпись launch-данных относится к боту запуска.

## Хранение

profile_contact_evidence сохраняет контакт, точный URL исходной web_app-кнопки без launch-фрагмента, аккаунт Jardulik, профиль и locator исходного сообщения. Тип official_bot_ui означает операторское наблюдение в интерфейсе, а не криптографически проверенный ответ Jardulik API. data-mid хранится как непрозрачный DOM locator и не объявляется серверным Telegram message_id.

Наблюдение импортируется JSON через stdin:

```sh
jardulik import-contact < evidence.json
```

Команда доступна только настроенному оператору и проверяет текущий upstream аккаунт, доверенный source bot, URL и привязку профиля. Сетевых запросов она не делает. Повторный импорт идемпотентен; изменение URL сохраняется отдельной записью. Контакт показывается отдельной кнопкой в личке, только для соответствующего владельца и текущего аккаунта. Исходный JSON анкеты не меняется. Новые контактные данные включены в fingerprint суточного бэкапа.

## Приём новых контактов

Парсер принимает `business_connection`, `business_message` и `edited_business_message` через существующий long polling. Сначала владелец подключает свой Jardulik через `/connect`. Затем в BotFather включают поддержку Business у Companion, и владелец подключает его к выбранному чату официального Jardulik. Эти настройки доступа не включаются автоматически при деплое.

Владелец определяется по `BusinessConnection.user.id`. Подключение закрепляется за текущим аккаунтом Jardulik и поколением его сессии. Новая сессия требует нового подтверждённого события подключения; старое подключение не переносится между аккаунтами. Сообщение должно прийти непосредственно от числового `JARDULIK_BOT_ID` в его приватном чате, без пересылки и отправки другим Business-ботом. Остальные чаты не записываются.

Парсер связывает одну однозначную пару ссылок в клавиатуре карточки: исходную кнопку `/mutuals?targetUserId=…&noCheck=1` и контакт `https://t.me/<username>`. Точный входящий JSON и контакт сохраняются одной транзакцией в `profile_business_contacts`, отдельно от серверного JSON анкеты. Контакт можно получить до загрузки самой анкеты. Дубли Telegram updates не создают повторные записи, изменённая ссылка сохраняет историю. Подтверждение offset идёт после записи: ошибка SQLite останавливает обработку, чтобы Telegram мог повторно доставить update.

Приём не отправляет сообщения от лица владельца и не отмечает их прочитанными. Показ сохранённого контакта использует только БД. Уже найденный контакт остаётся в архиве после отключения Business-чата, но скрывается при отключении или смене Jardulik-аккаунта. В суточный fingerprint входят контакты, точные новые исходные сообщения и состояние подключения. Повторная доставка того же Telegram update не считается обновлением; новое сообщение сохраняется отдельной квитанцией, даже если контакт не изменился.

## Автоматический запрос контактов

Роль `bot-parser` проверяет свежий список взаимностей раз в сутки. Подтверждённая новая взаимность в ответе обычного лайка ставит ближайшую проверку без ожидания суток; сам сборщик лайков не отправляет. Открытый пользователем свежий список взаимностей тоже создаёт задания. Очередь не использует старые пачки без подтверждённой привязки аккаунта.

Для работы нужны активное Business-подключение к текущей сессии Jardulik и работающая сессия источника. Пользовательская пауза, защитная пауза Jardulik, отключение или смена аккаунта блокируют HTTP. Перед отправкой проверяется состояние аккаунта. Запросы выполняются по одному с паузами, пользовательские команды получают приоритет.

Для взаимной анкеты без сохранённого контакта выполняется один `POST /telegram/getTG` с `fromUserId` и `targetUserId`. Пустой успешный HTTP-ответ означает ожидание карточки, а не наличие контакта. Исходные тело запроса, ответ и HTTP-статус записываются отдельно от серверного JSON анкеты. Ссылка появляется после подтверждённого сообщения официального бота. Уже сохранённый контакт не запрашивается заново.

Перед POST токен можно обновить штатным способом. После отправки нет автоматического повторения POST при 401, сетевом сбое, потерянном ответе или перезапуске процесса. Незавершённая отправка становится `unknown`; успешный запрос без пришедшей карточки остаётся `awaiting_receipt`. Эти состояния не сбрасываются новым поколением сессии или повторной выдачей той же анкеты. Ошибка чтения перед отправкой откладывает следующую попытку, а свежий список взаимностей может подтвердить ещё не отправленное задание заново.

Карточка может прийти раньше завершения HTTP-запроса. Приёмник атомарно сохраняет контакт и отмечает задание `received`, а завершение HTTP сохраняет ответ, сохраняя это состояние. Ошибка SQLite до отправки не допускает POST; ошибка записи результата останавливает контактный воркер.

Все новые сообщения выбранного официального бота сохраняются в `business_contact_inbox` точным входящим JSON после проверки владельца, источника и текущей сессии. Неоднозначный или новый формат остаётся `unresolved`, без придуманной связи с анкетой. Истёкшая HTTP-авторизация Jardulik не мешает приёму по прежнему действующему Business-подключению с той же привязкой аккаунта. Новое редактирование старой карточки проверяется по дате редактирования. Остальные чаты не попадают в этот архив. Новые исходные сообщения и результаты запросов включены в суточный бэкап; повторное чтение и технические изменения расписания не создают лишнюю копию.

`/status` показывает число сохранённых контактов и состояние очереди. Обычный обход каталога не раскрывает контакты анкет без взаимности. В просмотренных полных анкетах и списках взаимностей Telegram-поля не было; наличие URL в ответе самого `getTG` пока не подтверждено, поэтому парсер не предполагает схему этого ответа.

Business-подключение владельца активировано 9.11.2026 с одним выбранным чатом `@jardulik_bot`. Событие подключения принято в рабочую БД; права отправки, удаления и изменения аккаунта отсутствуют. Автоматическое получение новой контактной карточки ещё требует живой проверки. Существующий MTProto helper авторизован как наш бот, не как пользователь.
